## Changes Since v0.1.41

A one-line runtime fix for deployments that lock the handoff to WebClient pages.

- **The bundle-handoff redirect no longer discards the WebClient initiator.** The security middleware stamps `Referrer-Policy: no-referrer` on every response, including the `302` from `?sessiondata=` to `?bundleUrl=`. Browsers apply a redirect's `Referrer-Policy` to the request that follows it, so the follow-up viewer request arrived without `Referer` and the handoff guard rejected the gateway's own redirect with `403` whenever `webClientHandoff.allowedInitiatorUrls` was configured. The redirect now carries `strict-origin-when-cross-origin`, which keeps the same-origin initiator visible and still hides the path from cross-origin destinations. The HTTP-level test performs the full prep, handoff and follow-up sequence, was proven red without the header, and also proves that the follow-up without `Referer` is still rejected.
- **`web.config` no longer emits its own `Referrer-Policy`.** IIS appends `customHeaders` after the application's headers and browsers honour the last value, so the IIS copy of `no-referrer` would have silently undone the fix above in every IIS deployment (found by review against a live IIS response). The application middleware is now the header's only owner; `X-Frame-Options` and `X-Content-Type-Options` stay in `web.config`.

## Upgrade Guidance

Drop-in for v0.1.41 deployments. Deployments that worked around the rejection by clearing `allowedInitiatorUrls`, enabling `allowMissingInitiatorHeaders`, or disabling `useBundleUrlHandoff` can restore the intended configuration after upgrading.
