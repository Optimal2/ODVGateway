## Changes Since v0.1.43

Server-side PDF signature validation, off by default, plus the shared OMP theme on the gateway's own pages.

- **New: `GET /signatures/{sessionKey}/{fileIndex}` validates PDF signatures on the server.** For a file in a prepared session the gateway reports, per signature, `integrity` (intact, modified-after-signing, digest-mismatch, signature-invalid, unsupported, unreadable), `trust` (valid, invalid, unknown) with a reason code, signer and issuer, signing time and its source, document timestamps and whether the signature covers the whole file. Validation runs in bounded memory and time, never persists or caches document bytes, and uses the same session, index and byte-source resolution as `/source`. OpenDocViewer v2.11.0 shows the verdicts next to its own browser-side integrity check. See `docs/PDF-SIGNATURE-VALIDATION.md`.
- **Disabled by default and fully configurable.** `signatures.enabled` is `false` in a fresh checkout and in the packaged `appsettings.json`: the endpoint answers 404 and nothing is loaded, so existing deployments behave exactly as before. When enabled, `revocationMode` chooses `Online` (issuer CRLs fetched through the gateway's own bounded transport: public addresses only, optional exact host allow-list, 1–30 s timeout, AIA and OS downloads disabled), `Offline` (CRL files from `crlDirectory` only, no network) or `NoCheck` (no revocation, verdict always `unknown`). `useWindowsTrustedRoots`, `extraAnchorsDirectory`, `maxFileBytes` and `maxConcurrentValidations` complete the surface. A deployment that puts speed and stability first keeps the feature off or runs it `Offline`/`NoCheck`.
- **Exact object references in signature validation.** References are resolved exactly by (number, generation), as the PDF specification requires, so an appended `N 1 obj` can never shadow a signed field, signature dictionary, AcroForm or catalog that the document references as `N 0 R`. An incremental update that rewrites objects under a higher generation number (`5 1 obj` while references still say `5 0 R`) is outside the specification: the referenced generation-0 objects are read, and a signature covering the earlier revision is reported as modified after signing, as strict readers show it. Only a reference whose exact entry is missing from the cross-reference data falls back to the newest generation; the response then carries `reference-generation-fallback` in its new document-level `diagnostics` array. Rule 5 (an earlier approval signature stays intact only when a later intact signature covers its revision) and the traversal bounds are unchanged.
- **Hardening of the validation path**, found by review before release: integrity, trust and revocation gaps closed (detached CMS content handed to the verifier, strict ByteRange gap check, certification signatures with appended bytes stay invalid), archived CRL selection fixed, base CRLs that advertise unsupported delta CRLs rejected, asynchronous validation bounded by the file budget.
- **Process isolation for signature validation.** With the default `signatures.isolateProcess: true`, each file is validated in a separate worker process (the same assembly as `ODVGateway --signature-worker`, document bytes over stdin, JSON over stdout, never a temp file) supervised with a 30-second wall-clock timeout and a 512 MiB memory cap under the existing concurrency limiter. A worker that crashes, times out, overruns memory or answers unparseably costs one request — a named HTTP 503 (`validation-worker-crashed`, `validation-worker-timeout`, `validation-worker-memory`) — while the gateway keeps serving; a small warm pool (at most two idle workers, retired after 25 requests or any failure) keeps the per-request cost near the in-process one. The page-tree pre-check remains as the cheap first line. `isolateProcess: false` keeps the in-process path for trusted archives only.
- **Status and error pages follow the shared OMP light/dark theme**, with hardened theme-cookie parsing and themed renderer failures covered by tests. Unknown-length proxy responses are validated. Static web assets get a pinned `Last-Modified`, so the web artifact is reproducible.
- **Known limitation (validation enabled only).** A pre-open page-tree check rejects the measured stack-overflow shapes for files with classic cross-reference tables (cyclic `/Pages` → `/Kids` chains, self-referencing nodes, malformed `/Kids` entries) with a named HTTP 422 failure before PdfPig opens the file. Files whose cross-reference is a stream (xref streams / object streams, i.e. most modern producers) pass through to PdfPig without the pre-check, and catalog `/Dests` and `/Names` trees are not pre-checked either — but with the default `signatures.isolateProcess: true` (campaign `odvgateway-signaturvalidering-i-separat-process`) one crafted file of those shapes can only cost its own request (a named HTTP 503), never the gateway process. With `signatures.enabled: false` (the default and every VGR profile) the endpoint never opens a file, so there is no exposure. Only `signatures.isolateProcess: false` still requires a trusted archive.
- **Tests, CI and tooling.** The local CI gate runs the canonical OMP Pester step and the shared-script check (Check 15) through the shared resolver; smoke stack-frame detection fixed; 318 unit tests. No known vulnerable packages (`dotnet list package --vulnerable --include-transitive`).

## Upgrade Guidance

Drop-in for v0.1.43 deployments: no configuration change is required and no new network traffic occurs unless `signatures.enabled` is set to `true`. To offer signature verdicts in the viewer, set `signatures.enabled: true` in the deployment's configuration overlay and pick a `revocationMode` the environment allows — `Offline` or `NoCheck` need no outbound access, `Online` needs the servers to reach the issuers' CRL endpoints (restrict them with `revocationHostAllowList`). OpenDocViewer v2.11.0 or later is needed to display the verdicts; older viewers ignore the endpoint.
