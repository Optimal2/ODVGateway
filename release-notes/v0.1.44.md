## Changes Since v0.1.43

Server-side PDF signature validation (off by default; when enabled, each file is checked in an isolated worker process), the shared OMP theme on the gateway's own pages, a startup warning when the bundle-URL handoff is disabled, and a CycloneDX SBOM attached to the release. Dependencies are refreshed, and no known vulnerable packages remain.

- **New: `GET /signatures/{sessionKey}/{fileIndex}` validates PDF signatures on the server.** For a file in a prepared session the gateway reports, per signature, `integrity` (intact, modified-after-signing, digest-mismatch, signature-invalid, unsupported, unreadable), `trust` (valid, invalid, unknown) with a reason code, signer and issuer, signing time and its source, document timestamps and whether the signature covers the whole file. Validation runs in bounded memory and time, never persists or caches document bytes, and uses the same session, index and source resolution as `/source`, reading the bytes through the `/source-pack` reader. A PDF above an explicitly set, lower `signatures.maxFileBytes` answers HTTP 413. A PDF above `maxSourcePackFrameBytes` (64 MiB unless changed, and the only configurable limit while `maxFileBytes` is 0; the isolated worker also refuses files above 256 MiB, see Upgrade Guidance) answers HTTP 404 with the source-pack size message, because the source reader refuses it first. OpenDocViewer v2.11.0 shows the verdicts next to its own browser-side integrity check. See `docs/PDF-SIGNATURE-VALIDATION.md`.
- **Disabled by default and fully configurable.** `signatures.enabled` is `false` in a fresh checkout and in the packaged `appsettings.json`: the endpoint answers 404 and nothing is loaded, so existing deployments keep their behaviour, except for one startup check on the worker memory cap that runs even while the feature is off (see Upgrade Guidance). When enabled, `revocationMode` chooses `Online` (issuer CRLs fetched through the gateway's own bounded transport: direct connections to public addresses only, no HTTP proxy, no OCSP, optional exact host allow-list, 1–30 s timeout, AIA and OS downloads disabled), `Offline` (CRL files from `crlDirectory` only, no network) or `NoCheck` (no revocation check: a signature that would otherwise be `valid` reports `unknown` with `revocation-not-checked`; broken, weak or chain-policy-violating signatures still report `invalid`). `revocationTimeoutSeconds` (default 15), `revocationHostAllowList`, `useWindowsTrustedRoots`, `extraAnchorsDirectory`, `maxFileBytes` (the default 0 follows `maxSourcePackFrameBytes`) and `maxConcurrentValidations` (default 2) complete the validation settings; `isolateProcess`, `workerTimeoutSeconds` and `workerMaxMemoryBytes` control the worker (below). A deployment that puts speed and stability first keeps the feature off or runs it `Offline`/`NoCheck`.
- **Exact object references in signature validation.** References are resolved exactly by (number, generation), as the PDF specification requires, so an appended `N 1 obj` can never shadow a signed field, signature dictionary, AcroForm or catalog that the document references as `N 0 R`. An incremental update that rewrites objects under a higher generation number (`5 1 obj` while references still say `5 0 R`) is outside the specification: the referenced generation-0 objects are read, and a signature covering the earlier revision is reported as modified after signing, as strict readers show it. Only a reference whose exact entry is missing from the cross-reference data falls back to the newest generation; the response then carries `reference-generation-fallback` in its new document-level `diagnostics` array. A dangling reference, a cyclic reference chain, a value of the wrong type or a chain longer than the depth limit inside the field, widget and annotation walk is skipped, so the remaining signatures are still validated, and `diagnostics` names each case (`dangling-reference-skipped`, `reference-cycle-skipped`, `unexpected-object-type-skipped`, `reference-depth-exceeded`): no field, `/V` or signature dictionary is skipped silently. A cyclic `/AcroForm` reference fails the file with HTTP 422 instead of reading as a document without signatures. A fallback never makes a signature `intact` on its own: an earlier approval signature with appended bytes stays `intact` only when a later, itself intact signature covers its revision and the current file, and fallback references obey the same traversal limits.
- **Validation hardening from review before release.** Integrity, trust and revocation gaps were closed: detached CMS content is handed to the verifier, ByteRange gaps are checked strictly, certification signatures with appended bytes stay invalid, archived CRL selection is fixed, base CRLs that advertise unsupported delta CRLs are rejected, and asynchronous validation is bounded by the file budget.
- **Process isolation for signature validation.** With the default `signatures.isolateProcess: true`, each file is validated in a separate worker process (the same assembly as `ODVGateway --signature-worker`, document bytes over stdin, JSON over stdout, never a temp file) supervised with a wall-clock timeout (`signatures.workerTimeoutSeconds`, default 30 s) and a memory cap (`signatures.workerMaxMemoryBytes`, default 512 MiB) within the `signatures.maxConcurrentValidations` slots (no queue: when every slot is busy the endpoint answers 503 with `Retry-After: 1`). A worker that crashes, times out, overruns memory or answers unparseably costs one request — a named HTTP 503 (`validation-worker-crashed`, `validation-worker-timeout`, `validation-worker-memory`) — while the gateway keeps serving; a small warm pool (at most two idle workers, retired after 25 requests or any failure, and not reused after five idle minutes) keeps the per-request cost near the in-process one. Worker write failures, including closing stdin of a worker that already died, map to the same named 503 instead of a raw 500. Two worker misconfigurations are refused at startup with a named reason, even while `signatures.enabled` is `false`, instead of failing per request: a test-only `signatures.workerTestMode` without its environment gate, and a `signatures.workerMaxMemoryBytes` below three times the effective file budget. The page-tree pre-check remains as the cheap first line. `isolateProcess: false` keeps the in-process path for trusted archives only.
- **Startup warning when the bundle-URL handoff is disabled.** With `useBundleUrlHandoff: false` the gateway now logs a warning at startup: without the `?bundleUrl=` redirect, OpenDocViewer inside the WebClient page prefers the host page's own payload, so the viewer can bypass the prepared gateway session and its source-pack transport and fetch every source directly from WebClient. When `webClientHandoff.allowedInitiatorUrls` is set, the warning adds that the deployment is a WebClient handoff deployment and is affected. The setting itself behaves as before.
- **Status and error pages follow the shared OMP light/dark theme.** They read the shared `OMP_THEME_PREFERENCE` cookie without adding script or changing the default Content-Security-Policy; a malformed cookie falls back to the system palette. Theme-cookie parsing is hardened, and themed renderer failures are covered by tests.
- **Unknown-length source proxy responses are checked before delivery.** A proxied `/source` response without `Content-Length` is read and checked against `maxSourceProxyBytes` in full before a success status is sent, so an oversized body returns HTTP 502 instead of failing mid-stream. Bodies above 64 KiB are buffered in `ASPNETCORE_TEMP` (or the process temp directory) and removed when the request finishes; the first response byte waits for the check. A transfer that fails after the response has started is logged and the client connection aborted, instead of fetching the source from WebClient again.
- **Known limitation (validation enabled only).** A pre-open page-tree check rejects the measured stack-overflow shapes for files with classic cross-reference tables (cyclic `/Pages` → `/Kids` and `/Type` chains, self-referencing nodes, malformed `/Kids` entries) with HTTP 422 before PdfPig opens the file. Files whose cross-reference is a stream (xref streams / object streams, i.e. most modern producers), hybrid-reference files and encrypted files pass through to PdfPig without the pre-check, and catalog `/Dests` and `/Names` trees are not pre-checked either — but with the default `signatures.isolateProcess: true` one crafted file of those shapes can only cost its own request (a named HTTP 503), never the gateway process. With `signatures.enabled: false` (the default) the endpoint never opens a file, so there is no exposure. Only `signatures.isolateProcess: false` still requires a trusted archive.
- **Dependencies.** NLog.Web.AspNetCore 6.2.2. Signature validation adds two runtime packages: PdfPig 0.1.16 (Apache-2.0) and System.Security.Cryptography.Pkcs 10.0.13. Pkcs 10.0.13 fixes two .NET denial-of-service advisories in 10.0.12: CVE-2026-84008 (high; CPU exhaustion in `SignedCms.CheckSignature`, which signature validation calls) and CVE-2026-70162 (moderate; `EnvelopedCms` on Windows, which the gateway does not use). v0.1.43 did not include the package; the interim OMP artifacts 0.1.57–0.1.72 built from main carried 10.0.12. `dotnet list package --vulnerable --include-transitive` reports no vulnerable packages.
- **Software bill of materials.** Starting with this release, each GitHub release carries `ODVGateway-sbom-vX.Y.Z.cdx.json` next to the archive: a CycloneDX JSON SBOM (CycloneDX .NET 6.3.1) of the published project and its project references, with test and development dependencies excluded. `SECURITY.md` has a new EU Cyber Resilience Act section covering coordinated vulnerability disclosure, the SBOM and the CRA reporting obligations that apply from 11 September 2026.
- **Tests, CI and build.** The local CI gate runs the canonical OMP Pester step and the shared-script check (Check 15) through the shared resolver; the canonical component-version validator helpers are synced from OpenModulePlatform; smoke stack-frame detection fixed. The shared OMP deterministic-build files are synced from OpenModulePlatform: the build maps the checkout directory out of the compiled output, so unchanged source built from another checkout path produces the same OMP artifact. 321 unit tests, on Microsoft.NET.Test.Sdk 18.11.0, xunit.v3 4.0.2, xunit.runner.visualstudio 4.0.1 and Microsoft.AspNetCore.Mvc.Testing 10.0.13.

## Upgrade Guidance

Drop-in for most v0.1.43 deployments: no new network traffic occurs unless `signatures.enabled` is set to `true`. Three checks:

1. **Raised source limits need a matching worker memory cap.** Startup refuses a `signatures.workerMaxMemoryBytes` (default 512 MiB) below three times the signature file budget, regardless of `signatures.enabled` and `signatures.isolateProcess`. That budget is the smaller of `signatures.maxFileBytes` (when set) and `maxSourcePackFrameBytes` (default 64 MiB). A deployment that raised `maxSourcePackFrameBytes` above about 170 MiB therefore fails to start after the upgrade until it either sets `signatures.maxFileBytes` to at most a third of the worker cap (for example `67108864`) or raises `signatures.workerMaxMemoryBytes` to at least three times `maxSourcePackFrameBytes`. Independently of the cap, the isolated worker refuses any PDF above 256 MiB with HTTP 503 `validation-worker-crashed`; a `signatures.maxFileBytes` of at most `268435456` turns that into HTTP 413. The startup error names the setting; under IIS the site answers HTTP 500.30 and the message is in the Windows Application event log (and in the stdout log when `stdoutLogEnabled` is on).
2. **The temporary directory must be writable.** Proxied WebClient source responses without `Content-Length` are buffered above 64 KiB in `ASPNETCORE_TEMP` (or the process temp directory), so it needs room for concurrent responses.
3. **`useBundleUrlHandoff: false` now logs a startup warning.** Inside the WebClient page, restore `useBundleUrlHandoff: true`; keep it disabled only for a standalone viewer with no parent payload.

To offer signature verdicts in the viewer, set `signatures.enabled: true` in the deployment's configuration overlay and pick a `revocationMode` the environment allows — `Offline` or `NoCheck` need no outbound access, `Online` needs direct outbound HTTP/HTTPS from the servers to the issuers' CRL distribution points on public addresses. The transport uses no HTTP proxy, refuses private, loopback and link-local addresses and does not use OCSP. With proxy-only egress, or for an issuer whose CRLs are published on an internal host, those signatures stay `unknown` (`revocation-unavailable`) unless current CRL files for the issuers are placed in `crlDirectory`, which `Online` reads first. Restrict outbound fetches with `revocationHostAllowList`. OpenDocViewer v2.11.0 or later is needed to display the verdicts; older viewers ignore the endpoint.
